# CVE

## 大致了解

Google 搜索对应的 CVE，推荐查看：

- [NVD 美国官方漏洞数据库](https://nvd.nist.gov/)
- [CVE 官方](https://www.cve.org/)
- [GitHub Advisory Database](https://github.com/advisories)

查看其中的：

- 漏洞的大致描述
- 受影响的 Product
- 参考资料
- 漏洞发现者/团队

然后查看：

- 漏洞发现者/团队，或者
- Product 的 Vendor

是否写了专门的博客。

接着，搜索：

- Diff
- Poc/Exp

## 漏洞分析与复现

下载存在漏洞版本的项目源码，下载完成后用对应的 IDE 打开项目，并且根据提示将该项目所需依赖都安装上。

>[!tip]
> IDE 推荐使用 JetBrians 全家桶。

接着大致了解该项目，通过：

- README
- 官方主页介绍
- 官方文档（关注和本漏洞有关的部分）

随后对项目进行整体上的了解：

- 目录名
- 依赖
- 框架
- 前后端
- 中间件
- 路由

>[!tip]
> AI 时代还可以观察 `.claude`，里面会有一些提示词，根据你对 Vibe Coding 的了解去排查潜在的问题。

分析过程中，善用：

- IDE 的检索功能（全局、局部）
- [ripgrep](https://github.com/burntsushi/ripgrep) 工具
- IDE 的“go to（转到）”功能
- 针对审计部分画出/写出流程
- 调试
- 写测试代码
- 记录

## 一些注意事项

- 一些逻辑可能在依赖之中，而对于没有安装的依赖，IDE 并不能实现“go to”（这也是为什么先把依赖装齐的原因）
- 代码中的注释并不经常准确
- `rg` 默认会跳过隐藏目录（比如 `.test`），如果要包含，则需要带上 `--hidden` 参数
- 类中方法间的互相引用，IDE 的“go to”功能可能就没这么好使了
- 官方文档不一定准确、详细，而且官方文档是以开发者视角去写的，而非安全研究员视角，还得落实到具体代码上
